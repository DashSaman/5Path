# مشخصات معماری: سقف سخت مشترک TCP آلمان

**وضعیت: مشخصات با پاسخ صریح مالک تأیید شد؛ برنامهٔ پیاده‌سازی منتظر بازبینی است.**  
**دامنه:** آلمان، ورودی TCP با سقف قدیمی (K=4096).  
**تصمیم مالک در ۲۳ اکتبر ۲۰۲۶:** سقف کل ۴۰۹۶ حفظ شود؛ افزایش ۱۲۸ اتصال بومی و مجموع ۴۲۲۴ تأیید نشد.  
**مجوز این مرحله:** مالک پس از تأیید مشخصات، فقط نوشتن [برنامهٔ پیاده‌سازی](../plans/2026-10-23-de-shared-admission-plan.fa.md) را مجاز کرد. اجرای کد، fixture، ساخت binary، SSH، rollout یا تغییر سرور همچنان مجاز نشده است.

## مسئله

Gateway قدیمی، هر اتصال پذیرفته‌شده را پیش از handshake در `_connections` ثبت می‌کند و فقط پس از پایان کامل handler آزاد می‌کند. front بومی نامزد، شمارندهٔ مستقل دارد. این دو شمارنده مشترک نیستند؛ بنابراین سقف‌های مستقل، کران سخت مجموع را تضمین نمی‌کنند. snapshot دوره‌ای نیز شمارش اتمیِ پذیرش‌های درحال‌پرواز را جایگزین نمی‌کند.

سقف مورد توافق، تعداد کارهای کاربردی پذیرفته‌شده یا درحال handshake است؛ SYN/listen backlog کرنل معیار ظرفیت این قرارداد نیست. محدودیت حافظه، task و FD نیز جای سقف اتصال را نمی‌گیرد.

## هدف‌ها و معیارهای طراحی

1. در هر لحظه تعداد رزروهای معتبرِ مشترک بین Gateway قدیمی و front بومی از ۴۰۹۶ بیشتر نشود.
2. رزرو پیش از ساخت handler/task یا goroutine و پیش از handshake گرفته شود؛ رقابت هم‌زمان دو front نتواند رزرو ۴۰۹۷ را صادر کند.
3. اتصال‌های pending، احراز هویت‌شده، بی‌بایت، درحال انتقال و نیمه‌بسته تا پایان کامل lifecycle جایگاه خود را نگه دارند.
4. هر رزرو دقیقاً یک بار آزاد شود؛ خطای auth/backend، لغو یا close نیز مسیر آزادسازی امن و قابل‌آزمون داشته باشد.
5. خرابی، قطع دسترسی، ناسازگاری هویت یا state نامعتبرِ allocator فقط اتصال‌های **جدید** را fail-closed کند؛ جریان زنده را متوقف یا reset نکند.
6. مسیر داده همان مسیر مستقیم فعلی بماند؛ relay یا copy-loop تازه به dataplane اضافه نشود.
7. قرارداد به یک نسل، boot، کشور، K، binary، config، policy و هویت participantها مقید باشد؛ state نسل دیگر یا نامعلوم پذیرفته نشود.

## طرح پیشنهادی

یک مرجع پذیرش مشترک، برای هر دو نسل، رزرو یکتا و اتمی می‌دهد. هر دو participant پیش از شروع کار اتصال `reserve(identity)` را صدا می‌زنند؛ در صورت موفقیت، token غیرقابل‌حدس نگه داشته می‌شود. token فقط پس از پایان کامل handler و بسته‌شدن هر دو جهت آزاد می‌شود. آزادسازی idempotent است، اما خطای bookkeeping هرگز با reset شمارنده یا فرضِ انقضای زمانی جبران نمی‌شود.

allocator به‌تنهایی جریان را حمل نمی‌کند. روی نبود ظرفیت، participant فقط همان اتصال تازه را رد می‌کند. روی خطای allocator نیز پذیرش تازه بسته می‌ماند؛ اتصال‌هایی که قبلاً token گرفته‌اند ادامه می‌یابند.

### چرخهٔ token و بازیابی

هر رکورد باید حداقل شامل شناسهٔ یکتا، boot ID، شناسهٔ نسل/run، کشور، K، participant، PID به‌همراه start-time، cgroup/service identity و وضعیت رزرو باشد. PID تنها کافی نیست؛ PID reuse و فرزندانی که FD/socket را به ارث برده‌اند باید پوشش داده شوند.

- token دارای timeout نیست؛ اتصال idle یا handshake مجاز با گذشت زمان جایگاه را از دست نمی‌دهد.
- participant فقط token خودش را آزاد می‌کند؛ آزادسازی تکراری اثر دوم ندارد.
- پس از crash، reclaim فقط وقتی مجاز است که مرجع مستقل نشان دهد کل scope مالک socketها (فرایند، فرزندان و cgroup مربوط) دیگر زنده نیست. ابهام، mismatch یا عدم دسترسی یعنی fail-closed و رسیدگی دستی.
- boot جدید به‌تنهایی مجوز حذف state نیست؛ ابتدا هویت مالک، scope و نبود participant/socketهای boot پیشین باید با قرارداد قابل‌تأیید ثابت شود.
- lock/state file یا journal در زمان مشارکت‌ها unlink، truncate یا از نو مقداردهی نمی‌شود. خرابی یا schema ناشناخته، ظرفیت تازه اختراع نمی‌کند.

پیش از طرح implementation باید انتخاب شود که مرجع مشترک یک primitive فایل-قفل‌شدهٔ محلی باشد یا سرویس محلی با journal پایدار. این انتخاب هنوز انجام نشده است. هر گزینه باید اتمی‌بودن بین Python و Go، durability، crash recovery، permission، lock contention و fail-closed را اثبات کند.

## مانع انتقال با نسخهٔ فعال فعلی

نسخهٔ قدیمیِ فعال، در allocator پیشنهادی مشارکت نمی‌کند و فایل state فعلی آن نیز تعداد کامل handlerهای pending را منتشر نمی‌کند. front بومی مستقل هم نمی‌تواند این کمبود را با snapshot دوره‌ای جبران کند.

پس تا وقتی همهٔ ورودی‌های قدیمی به مرز پذیرش مشترک نرسیده‌اند یا نسخهٔ قدیمی در یک انتقال کنترل‌شده به participant allocator تبدیل نشده، **اجرای هم‌زمان old و native با سقف سخت ۴۰۹۶ قابل تأیید نیست**. بازکردن گیت native با `N>0` در این وضعیت ممنوع می‌ماند. تبدیل نسخهٔ درحال اجرا به participant، بدون بارگذاری نسل تازه یا تغییر مرز ورودی ممکن نیست. تعویض فرایند قدیمی می‌تواند اتصال‌های بازش را قطع کند؛ این سند هیچ انتقال یا maintenance window را مجاز نمی‌کند. اگر انتقالی که اتصال‌های جاری را حفظ می‌کند قابل طراحی/اثبات نباشد، تصمیم امن freeze ماندن DE است.

## گزینه‌ها و trade-off

| گزینه | سقف سخت K | هزینه/محدودیت | وضعیت |
|---|---|---|---|
| allocator اتمی مشترک، هر دو participant | ممکن است؛ نیازمند lifecycle واقعی هر دو نسل | نیاز به قرارداد cross-language، بازیابی crash و انتقال نسل قدیمی | گزینهٔ پیشنهادی برای طراحی آینده؛ هنوز پیاده‌سازی‌نشده |
| proxy مشترک در مسیر داده | بالقوه می‌تواند ورودی هر دو را بشمارد | relay/copy اضافه و هزینهٔ dataplane؛ نمونهٔ relay پیشین به‌علت CPU بیشتر رد شد | توصیه نمی‌شود |
| حفظ نسخهٔ فعلی و freeze نصب DE | سقف فعلی را دست‌کاری نمی‌کند | بهبود native DE ارائه نمی‌دهد | پیش‌فرض امن تا اثبات راه انتقال |
| بودجهٔ مستقل N برای native | مجموع K+N می‌شود | سقف سخت ۴۰۹۶ را می‌شکند | مالک رد کرده؛ خارج از دامنه |

## آزمون‌های لازم پیش از هر پیاده‌سازی یا rollout

این‌ها معیار طراحی‌اند، نه دستور اجرای فعلی:

- آزمون unit/property با K کوچک برای هم‌زمانی reserve در دو participant و ناوردای `reserved <= K`؛ سپس آزمون عددی K=4096 بدون ساخت ۴۰۹۶ جریان واقعی.
- fixture بین دو فرایند واقعی Python و native: K اشغال، N+1 رد پیش از backend، دو رزرو هم‌زمان در مرز K، و participant نسل ناشناخته رد شود.
- pending handshake، احراز هویت موفق/ناموفق، backend error، cancellation، FIN یک‌طرفه و teardown کامل؛ SHA payload و PID جریان‌های باز حفظ شود.
- allocator unavailable، state خراب، permission/schema mismatch و failover کنترل‌شده؛ فقط اتصال تازه رد شود و survivorها ادامه دهند.
- crash participant با PID reuse شبیه‌سازی‌شده، فرایند/فرزند در cgroup، boot ID و reclaim؛ هیچ token زنده یا نامعلوم آزاد نشود.
- برابری شمار allocator با شمار handlerهای واقعی در fixture از لحظهٔ accept تا پایان handler؛ نه شمار listener-port و نه snapshot دوره‌ای oracle قابل قبول نیست.
- پس از قبولی correctness، فقط هزینهٔ رزرو برای اتصال جدید، contention، حافظهٔ state و CPU فرایندهای allocator/worker جداگانه سنجیده شود. این‌ها به‌تنهایی کاهش CPU کل سرور را ثابت نمی‌کنند.
- همهٔ فرزندان، socketها، ruleها و فایل‌های موقت fixture باید با receipt پاک‌سازی شوند؛ WAN و SSH صفر.

## گیت تغییر و rollout

گیت فعلی نصب بسته می‌ماند. پیش از هر آزمایش تولیدی، monitor سالم، baseline کامل ۳۰۰ثانیه‌ای CPU/RAM، ممیزی تازهٔ namespace/route/rule/NAT/config/listener/peer/ephemeral، مالکیت و clock معتبر، root/CID/key/port/nonce/deadline تازه و guard مستقل با lease حداکثر ۱۰ ثانیه لازم است. آزمایش محدود یک کشور و یک فایل 16KiB است. هیچ فایل hashed یا سرویس committed درجا تغییر نمی‌کند و هیچ فرایندی خودکار stop/restart/cleanup نمی‌شود. T6، XUI، carrierها، کاربران، مسیرهای UDP و اتصال‌های باز خارج از دامنه‌اند.

پیش از rollout، descriptor immutable باید binary، config، K=4096، schema، policy hash، boot/run، cgroup/service identity، participantها و lifecycle start/stop/recovery را به هم متصل کند. worker و watchdog باید همین هویت را بخوانند. وجود فایل allocator یا unit تازه، به‌تنهایی معیار پذیرش نیست.

## خارج از دامنه و ادعاهای ممنوع

این طراحی کاهش CPU کل، افزایش ظرفیت، latency بهتر، بازی واقعی، حفظ نشست هنگام تعویض فرایند یا کیفیت معادل T6 را ثابت نمی‌کند. WARP، UDP، کشورهای دیگر، XUI، T6، مسیر کاربران، DNS/NTP و tuning عمومی سیستم در دامنه نیستند. هیچ benchmark قدیمیِ جواب‌گرفته یا روش listener-port متوقف‌شده تکرار نمی‌شود.
