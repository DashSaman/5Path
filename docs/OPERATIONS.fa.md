# راهنمای عملیات و تغییر امن

## مرز تغییرات

این مخزن کپی تنظیمات خصوصی میزبان‌ها نیست و دستور نصب خودکار روی تولید ارائه نمی‌دهد. T6، XUI، پنل، routing کاربران، تونل‌های موجود دیگران و سرویس‌های تحویل‌شده، بدون دستور صریح متناسب تغییر نمی‌کنند. انتخاب کشور و انتقال کاربران با مالک است.

دستور جدید مالک برای WARP فقط US-5PATH است. دستور بهینه‌سازی CPU و کیفیت، فقط مسیرهای خودمان در چهار کشور را پوشش می‌دهد. نصب پکیج عمومی، تعویض binary تولیدی دیگران، تغییر default route، DNS/NTP سراسری، MTU یا qdisc اصلی، firewall عمومی و restore snapshot قدیمی در این دامنه نیست.

## ترتیب لازم پیش از تغییر سرور

1. آخرین checkpoint، پیام تازهٔ مالک و رسید واقعی خوانده شود. متن اتوماسیون جای مدرک تازه نیست.
2. PID و زمان شروع کنترلر بررسی شود. کنترلر، SSH worker یا آزمایش زندهٔ موازی ایجاد نشود.
3. SSH به میزبان دقیق با host-key pin تأیید شود. credential در RAM یا فایل خصوصی بماند و وارد argv، کد، لاگ، گزارش یا مخزن نشود.
4. ساعت میزبان‌ها با بازهٔ عدم‌قطعیت بررسی شود، یا deadline مستقل هر میزبان به‌طور معتبر اثبات شود. اختلاف ساعت نباید انقضا را ساعت‌ها عقب بیندازد.
5. مانیتور تازه و CPU کامل ۳۰۰ثانیه‌ای روی مشارکت‌کننده‌های لازم بررسی شود. CPU وزنی بالاتر از ۸۵٪، RAM پایین، telemetry قدیمی یا نامعتبر، شروع payload را متوقف می‌کند. spike کوتاه معیار نیست.
6. IPv4/IPv6، route/rule، listenerها، اتصال‌های برقرار با source و peer، NAT، native nftables، کانفیگ‌های مرتبط، پورت موقت و reserved، namespace نام‌دار و بی‌نام ممیزی شوند.
7. root، شناسه، پورت، کلید کنترل، nonce و deadline تازه ایجاد شوند. آماده‌سازی منقضی یا failed هرگز restart، adopt یا resume نشود.
8. guard و worker مستقل از مدل و SSH، با lease حداکثر ۱۰ثانیه‌ای و deadline مستقل آماده شوند. وضعیت warming به‌جای ۳۰۰ثانیهٔ کامل پذیرفته نشود.
9. فقط یک کشور و یک فایل کوچک 16KiB در هر نوبت بررسی شود. در تداخل منابع، تنها آزمایش خودمان متوقف شود.
10. پیش از commit، فایل‌های boot هر دو نقش، hash، PID/start/cgroup، وضعیت unit و `NRestarts=0` ثبت شوند. پس از commit نیز post-guard، handoff-ready و exit واقعی کنترلر لازم است.

در آماده‌سازی ترمینال، `prepare-aborted`، خروج ۷۸ و `RestartPreventExitStatus=78` حفظ می‌شوند. افزایش TTL برای پنهان‌کردن timeout یا غیرفعال‌کردن اعتبارسنجی TLS مجاز نیست.

## حفظ اتصال فعال

تغییر مسیر برای اتصال جدید با حفظ نشست موجود یکی نیست. پیش از هر restart، تعداد و هویت اتصال‌های واقعی باید بررسی شوند؛ کم‌شدن مصرف CPU یا گزارش انتقال کاربران، اثبات بی‌کار بودن فرایند نیست.

اصلاح ظرفیت قبلی از SYN-only redirect استفاده کرد و فرایند قبلی را زنده نگه داشت. تغییر بعدی نیز باید منابع قبلی را بشناسد و rule جدید را دقیقاً به source، destination، پورت جدید و comment متعلق به همان تغییر محدود کند. rule عمومی، flush، stop سرویس کاربران و دست‌کاری T6 مجاز نیست.

## cleanup

پاک‌سازی تنها برای منابع uncommitted همان اجراست، آن هم پس از تطبیق owner، PID/start، cgroup، unit و rule. منابع committed یا با مالکیت نامعلوم خواندنی می‌مانند. نام مشابه یا وجود فایل در یک مسیر، اثبات مالکیت نیست. snapshot قدیمی نباید روی وضعیت جدید نوشته شود.

برای ریشهٔ منقضی TR، ابتدا انقضای lease، نبود process/unit/cgroup و نبود rule مربوط به همان run بررسی می‌شود. فقط همان ریشهٔ دقیق پس از احراز همهٔ شروط قابل حذف است؛ آزمایش قبلی دوباره راه‌اندازی نمی‌شود.

## منابع و CPU

در سابقهٔ پروژه، hard CPU quota باعث معطلی و افت کیفیت شده بود و از dataplane حذف شد. `CPUWeight=5`، `Nice=10` و سقف RAM برای حفظ اولویت تولید باقی ماندند. این مقادیر جلوی هزینهٔ پردازش هر بایت را نمی‌گیرند. کم‌کردن سهم CPU بدون کاهش کار اضافی، ممکن است پینگ را بیشتر کند.

در ممیزی، فقط cgroup غیرخالی و واقعاً متعلق به unit فعال قابل انتساب است. دادهٔ cgroup ریشه، مصرف یک سرویس خاموش نیست.

## ثبت و محرمانگی

هر تغییر باید منبع، SHA، گیت‌ها، پیش‌شرط‌ها، نتیجه، محدودیت و وضعیت cleanup خود را داشته باشد. کانفیگ‌های خصوصی، کلیدها، CA خصوصی، sessionهای کنترلر، credential پنل، WARP و SSH در محیط خصوصی نگه داشته می‌شوند. شواهد عمومی با انتخاب صریح فیلدها ساخته می‌شوند؛ کپی کامل JSON خصوصی مجاز نیست.

انتشار GitHub، نصب روی سرور یا ارسال PDF را انجام نمی‌دهد. PDF نهایی تنها پس از تکمیل واقعی و بررسی همهٔ صفحات، با تأیید هویت مقصد و ثبت SHA/رسید، یک‌بار ارسال می‌شود.

برای مدیریت pinned، شمارهٔ رکورد احراز هویت موفق همراه با pin میزبان به‌صورت خصوصی نگه‌داری می‌شود؛ خود رمز در آن فایل ذخیره نمی‌شود. اتصال بعدی همان میزبان فقط همان credential تأییدشده را یک‌بار امتحان می‌کند. رد دسترسی، مجوز تغییر حفاظت، password reset یا آزمون پشت‌سرهم رمزها نیست. مسیر مدیریت مستقیم موجود فقط پس از اثبات mapping دقیق همان کشور و host key معتبر استفاده می‌شود؛ سرویس حامل و پیکربندی آن تغییر نمی‌کند.
