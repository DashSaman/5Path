# سیاست نسخه‌بندی و انتشار

درخواست مالک این است که هر نوبت تغییر منتشرشده، Release مستقل داشته باشد. واحد انتشار در این مخزن یک commit روی `main` است؛ تغییرهای محلی پیش از ثبت نهایی، یک نسخهٔ جدید عمومی محسوب نمی‌شوند.

## روند خودکار

1. تغییر کد، سند یا شواهد در یک commit قابل بررسی ثبت می‌شود.
2. workflow آزمون‌ها، syntax، لینک‌های محلی و خروجی عمومی را بررسی می‌کند.
3. فقط در صورت موفقیت، برای همان commit شمارهٔ یکتای `v0.1.<run_number>` ساخته می‌شود.
4. Release با یادداشت فارسی، ZIP کد همان commit و `SHA256SUMS` منتشر می‌شود.
5. فایل یادداشت انتشار مشخص می‌کند این نسخه شامل چه تغییرهایی است و چه چیزهایی هنوز نصب یا تأیید نشده‌اند.

نسخه‌ها فعلاً پیش‌انتشارند. شمارهٔ Release، شاهد موفقیت روی سرور یا کیفیت کاربران نیست. نتیجهٔ CI به معنی موفقیت آزمون WAN، capacity یا failover تولید نیست.

تغییرهای هم‌زمان به‌صورت مرتب منتشر می‌شوند و اجرای جدید، اجرای انتشار قبلی را لغو نمی‌کند. اجرای ناموفق Release قابل نصب تولیدی معرفی نمی‌شود؛ ابتدا همان خطا و commit بررسی و اصلاح می‌شوند.

## محتوای مجاز

کد عمومی، نمونه‌های مستندسازی، آزمون، سند فارسی و شواهد انتخاب‌شده قابل انتشارند. `work/`، خروجی‌های خام، session، دادهٔ کاربر، JSON خصوصی، کلید، فایل account/profile WARP و credential SSH/XUI نباید وارد commit یا asset شوند.

فایل‌های موجود در `core/` نسخهٔ عمومی پالایش‌شده‌اند. بعضی ثابت‌های شبکه با IP نمونه جایگزین شده‌اند. `evidence/source-index.json` SHA منبع داخلی و SHA نسخهٔ عمومی را برای تطبیق ثبت می‌کند. هیچ‌کدام مجوز کپی مستقیم روی تولید نیستند.

## یادداشت هر نسخه

یادداشت باید مسئله، تغییر، آزمون واقعی، اثر سرور و محدودیت را روشن بگوید. عبارت‌هایی مانند «محلی»، «خواندنی»، «نصب نشده» و «پذیرفته نشده» نباید با عبارت «کامل» جایگزین شوند. تغییر وضعیت WARP، TR UDP، ظرفیت یا ارسال PDF فقط با receipt واقعی ثبت می‌شود.

کلیدها و فایل خصوصی حتی در Release خصوصی یا asset فشردهٔ موقت هم به این روند افزوده نمی‌شوند. PDF پیش‌نویس جزو assetها نیست.
