# نتیجهٔ مرحلهٔ ۱: هزینهٔ پردازش و شمارنده‌های شبکه

**وضعیت: تشخیص محدود پایان یافت؛ اصلاح تولیدی تازه انجام نشد.** هدف این مرحله پیدا کردن شاهد برای اقدام بعدی بود. بار سنگین قبلی مشتریان در این مشاهده بازتولید نشد و کاهش CPU زیر بار برابر همچنان اثبات نشده است.

## چه چیزی واقعاً اندازه‌گیری شد

یک پنجرهٔ خواندنی حدود۶۰ثانیه‌ای روی ایران و سپس گیت‌وی ثبت شد. مانیتور گیت‌وی معتبر بود؛ پنجرهٔ کامل CPU آن۳۱۶ثانیه پوشش داشت. پس از مشاهدهٔ drop دریافت، فقط یک پیگیری۱۰ثانیه‌ای از شمارنده‌های درایور و ویژگی‌های همان رابط گیت‌وی انجام شد. این پنجره‌ها هم‌زمان یا دارای بار برابر نیستند.

| سنجه | ایران | گیت‌وی |
|---|---:|---:|
| طول پنجره | ۶۰٫۰۱ثانیه | ۶۰٫۱۱ثانیه |
| CPU مشغول، بدون iowait | ۴۵٫۴۵٪ | ۲۵٫۷۴٪ |
| سهم system از کل CPU | ۹٫۴۲ واحد درصد | ۱۰٫۱۷ واحد درصد |
| سهم softirq از کل CPU | ۱۳٫۰۸ واحد درصد | ۱۲٫۶۷ واحد درصد |
| CPU فرایندهای اختصاصی ما | پوشش ناقص؛ نامعلوم | مجموع چهار slice با فرزندان و worker/watchdog بومی: ۰٫۱۲۵۹۴ هسته |
| هویت سرویس‌های فعال ابتدای پنجره | ۸۰ سرویس بدون تغییر PID/state/NRestarts | ۱۴۸ سرویس بدون تغییر PID/state/NRestarts |
| retransmit ثبت‌شدهٔ TCP میزبان | ۴۱۶۹ | ۱۸ |
| drop دریافت رابط بیرونی در procfs | ۳۰ | ۲۹۵۳ |
| drop در softnet | صفر | صفر |

مصرف هستهٔ فرایند با درصد کل ماشین یک واحد نیست. شمارنده‌های TCP میزبان نیز سهم تونل، کاربر یا T6 را مشخص نمی‌کنند؛ نسبت retransmit به segment، درصد اتلاف فیزیکی شبکه محسوب نمی‌شود. روی ایران، ریشه‌های مورد انتظار collector برای چهار گروه موجود نبودند؛ مقدار اندازه‌گیری‌نشده «صفر» گزارش نشده است.

در گیت‌وی، ListenOverflows، ListenDrops، TCPBacklogDrop، TCPRcvQDrop، TCPMemoryPressures و خطای fragmentation/reassembly در این پنجره افزایش نداشتند. جدول TCP پورت‌های شناخته‌شده نیز ترافیک زیاد خودمان را نشان نمی‌داد؛ شمار socket معادل تعداد کاربر یا تمام handshakeهای خصوصی نیست. این شواهد علت فشار گذشته را تعیین نمی‌کنند.

## پیگیری drop دریافت؛ نتیجهٔ متفاوت در پنجرهٔ جدا

پیگیری۱۰٫۰۵ثانیه‌ای درایور `r8169` حدود۱۰۲هزار بستهٔ دریافت‌شده داشت. افزایش شمارنده‌های sysfs و درایور برای drop، missed، overrun، CRC و خطاهای دریافت/ارسال، صفر بود. بنابراین افزایش۲۹۵۳تاییِ پنجرهٔ اول در این پنجره تکرار نشد؛ علت اولیه همچنان **نامعلوم** است و «حل‌شده» محسوب نمی‌شود.

اندازهٔ RX/TX ring برابر۲۵۶ و همان حداکثر اعلام‌شده بود. GRO/GSO/TSO از قبل فعال بودند. پرس‌وجوی channel پشتیبانی نشد؛ این پاسخ نبود مطلق RSS را اثبات نمی‌کند. snapshot صف `fq` backlog صفر داشت؛ عدد۵۳۵۰۴۱ برای drop صف، تجمعی و تاریخی است و افزایشِ این پنجره نیست.

در نتیجه، مبنایی برای تغییر عمومی ring، offload، qdisc یا sysctl نداریم. شمارندهٔ procfs ممکن است چند نوع drop را جمع کند و به‌تنهایی اشباع کارت شبکه را ثابت نمی‌کند؛ تعریف سنجه‌ها در [مستندات رسمی آمار شبکهٔ Linux](https://docs.kernel.org/networking/statistics.html) و [شمارنده‌های SNMP](https://docs.kernel.org/networking/snmp_counter.html) آمده است.

## تصمیم و اقدام بعدی

مرحلهٔ ۱ با گزارش محدودیت پوشش و نبود شاهد کافی برای تنظیم عمومی شبکه بسته شد. تکرار خودکار همین مشاهده یا benchmark محلیِ پاسخ‌گرفته مجاز نیست.

مرحلهٔ ۲، آماده‌سازی **یک نامزد واسط TCP بومی آلمان** است. مقایسهٔ متوازن محلی قبلاً هزینهٔ کمتر خود مسیر داده را نشان داده؛ این قرینهٔ انتخاب نامزد است و رفع علت افت کیفیت گذشته یا بهبود کل سرور را ثابت نمی‌کند. کار مشخص بعدی، آزمون محلیِ سد پذیرش ورودی قدیمی و بودجهٔ محافظه‌کارانهٔ اتصال‌های باقی‌مانده است؛ اگر سقف مجموع و حفظ جریان‌ها قابل اثبات نبود، همین روش رد و دلیل و راه بعدی ثبت می‌شود. جزئیات و معیار پایان در [برنامهٔ اجرایی](WORK-PLAN.fa.md) است.

## شواهد و حدود انتشار

- [نتیجهٔ عددی پالایش‌شده](../evidence/tcp-quality-phase1.json) شامل پنجره‌ها، CPU، پوشش ناقص، شمارنده‌ها و نتیجهٔ پیگیری است.
- [collector خواندنی](../tools/tcp_quality_readonly_probe.py) و [collector درایور](../tools/rxdrop_readonly_probe.py) بدون helper اتصال یا credential منتشر شده‌اند. شناسهٔ ریشه و رابط در نسخهٔ عمومی از محیط محلی دریافت می‌شوند؛ این نسخه فقط syntax-check شده و مشاهدهٔ واقعی با اصل خصوصی انجام شده است.
- همهٔ اتصال‌های مدیریتی این مرحله بسته شدند. ترافیک آزمایشی ساخته نشد؛ کنترل سرویس، تغییر config، جابه‌جایی کاربران و تغییر T6 انجام نشد. مشاهدهٔ PID در دو انتها، تضمین پیوستگی بی‌وقفهٔ تمام خدمات بین آن دو لحظه نیست.
